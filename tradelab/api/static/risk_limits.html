What the engine refuses, and what it has refused.

LimitIn forceWhat it stops On breach

§12.4 puts sizing and risk limits in the operator's hands — unlike signal parameters, which cannot be edited anywhere, because changing one creates a new strategy that re-enters the funnel. What is not permitted is editing a configuration: §14.1 versions them and has each run reference one, so a limit never changes beneath a position opened under it. A change creates a new configuration and the old one stays readable beside the runs that used it. The engine evaluates these independently of the strategy and counts positions from observed fills, never from what the strategy reports: a strategy that miscounts its own state is the case these exist for.

Exactly one is active: the newest. That holds by construction rather than by a flag someone has to keep correct — a flag can be set on two rows, and a maximum cannot be reached twice. Two sharing a timestamp would make "newest" ambiguous, so the database refuses the tie.

Three of these are not a configured number. halted is a halt already in force, below_min_viable is a position too small to be worth its costs, and event_context is the one case where an order is allowed and carries a breach — news cutting the size down rather than refusing it.
